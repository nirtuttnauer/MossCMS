# Performance and scaling plan · 12 October 2026

Historical planning and implementation notes from 12–14 October 2026. Proposed work and intermediate states below remain dated records; use the current workflow guides and merged code for present support.

The owner requested faster ordering on any scalar schema field with automatic indexing, and asked about SQLite sharding and PostgreSQL writer/read replicas. The first implementation adds indexed scalar ordering and removes unused totals. OpenTelemetry now supplies request, GraphQL, SQL and worker measurements for choosing subsequent work. The target is low latency and predictable operating cost as content grows; being the best CMS requires evidence alongside features.

## How ordering works

A shared projection separates draft and published values. Exact filtering uses the existing bounded hash index and original-value recheck. Ordering reuses short binary prefixes as full values, stores full long values separately, and adds shared B-trees scoped by workspace, content type, snapshot and field. Numeric keys retain exact integer/float ordering; date keys represent calendar days. Short values can be read in index order with a small limit. The date index excludes non-date rows; the long-value index contains only fields needing the fallback. Long strings retain full-value ordering through a fallback that may need an additional sort. No content is converted to JSONB and accepted null-containing strings remain valid.

Cursors use value plus ID, bind the scope and direction, and put absent values in a separate null tail. They do not provide a transaction snapshot across pages while editors change content. `total` is lazy in GraphQL; the editor still requests it for its count. One top-level non-localized scalar field is supported per query; localized objects and multi-field sorts need explicit future contracts.

A matching B-tree can satisfy `ORDER BY ... LIMIT` without processing all results; multi-column mixed directions and distributions still influence planning. See [PostgreSQL ordering indexes](https://www.postgresql.org/docs/current/indexes-ordering.html) and [leading equality columns](https://www.postgresql.org/docs/current/indexes-multicolumn.html). The actual application plan, not merely an index's existence, determines whether the implementation benefits a workload.

## PostgreSQL writer/read separation

Keep writes, editorial reads, previews, revision restoration and scheduled publication on the primary. Delivery content could use a separate read-only pool when the caller accepts stale published data. Authentication, token revocation, workspace membership and private-field/schema visibility need primary-authoritative decisions; a stale replica schema must never expose a newly private field. Schema/publication epochs or a primary consistency boundary must be designed before routing such reads.

The initial optional reader URL should default to the primary. Add measured lag, connection/pool limits, cancellation handling, lag/unavailable fallback and read-your-publication checks before enabling a standby. Failover promotion, migrations and matched backups need a tested runbook. Replicas increase total read capacity; they do not make an inefficient query or a primary write cheaper. Asynchronous streaming replication can return stale data, documented in [PostgreSQL standby replication](https://www.postgresql.org/docs/current/warm-standby.html) and [hot standby](https://www.postgresql.org/docs/current/hot-standby.html).

The current API uses the same session for identity and content work. Blindly sending all reads to a replica would violate this consistency contract. No replica deployment or automatic query routing is included in the current implementation.

## SQLite sharding

A file per workspace could allow independent workspace writers, provided each file remains local to its host. WAL permits readers and a writer concurrently but still allows only one writer per database; a single busy workspace would retain that limit. Network filesystems are unsuitable for WAL, and transactions across attached databases are not atomic as a group. See [SQLite WAL concurrency and limitations](https://www.sqlite.org/wal.html).

MossCMS currently has shared accounts, memberships, tokens and workspace data with relational ownership. Sharding requires a central catalog, authoritative identity checks, a stable workspace-to-shard map, transaction boundaries, per-shard scheduler dispatch, migration orchestration and catalog-plus-shard recovery. Moving only entries to files would break existing relational and restore assumptions. Before building this, measure write-lock waits, transaction duration and tenant concentration; compare the simpler PostgreSQL deployment using the same workload.
