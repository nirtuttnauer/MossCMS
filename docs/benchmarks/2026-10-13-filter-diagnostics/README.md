# 100k filter diagnosis · 13 October 2026

A disposable 100k fixture was seeded using the previous sustained image, `mosscms:benchmark-d7a8348112a1` (source SHA256 `d7a8348112a1b1bf8b30d74eb4f5e496f425fc96f52b72dd4668996c9f4e0fe4`). The app/database fixture and main-workspace common category are unchanged. These SQL probes have no concurrent HTTP traffic and are separate from the sustained benchmark.

[Prepared plans](prepared-plans.json) compare the original exact-string count with a `CASE WHEN candidate-membership THEN true ELSE false END` predicate. PostgreSQL was explicitly set to `force_generic_plan` or `force_custom_plan`. Statements were manually prepared with the original bound fixture values, and each was explained three times; the saved plan is the last warmed repetition. The second plan in each pair is the unchanged filtered page query. The count's generic plan falls from 50.854 ms to 12.199 ms in this diagnostic: 20,000 primary-key entry probes and 20,000 content-type scope scans become one hashed candidate set and a covering delivery-index scan. This is a query-plan observation, not a mixed-load latency claim.

[Custom-plan and statistics experiments](custom-plans-and-statistics.json) also include common and absent values. Adding dependency/MCV statistics across project, type, snapshot, field and hash did not eliminate the count's per-entry probes and was not shipped. Forcing hashed membership increases empty-count work; the generic-plan regression checks common, rare and empty results. No prepared-plan configuration, new index, migration or database schema change was shipped.

The final implementation also omits the redundant token-scope subquery for named content types, after the existing `get_type` check verifies workspace and token scopes. Untyped lists retain the scope subquery. Source JSON still rechecks the node candidates, exact bytes and typed hashes still guard string totals, and all other scalar/null/coercion behavior is preserved. The original disposable diagnosis containers and volumes were removed.

The final [covering-plan probe](covering-prepared-plans.json) compares original, combined exact-candidate `CASE`, and separate hash/exact-value memberships. For this additional diagnostic only, `VACUUM ANALYZE` was run on the disposable fixture first to make covering-index visibility costs comparable. Three repetitions were again run per query/mode, saving the last. Generic count time was 52.192 / 13.667 / 12.981 ms respectively, with 89,561 / 10,878 / 1,158 shared buffer accesses. The final separate-membership shape lets the existing hash and prefix indexes each cover their own check. Long values still recheck the full binary key. Index-only execution depends on ordinary PostgreSQL visibility/vacuum conditions; the unchanged HTTP benchmark harness does not force vacuum. Its completed sustained latency data are the performance evidence.
