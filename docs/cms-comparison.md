# CMS comparison

This comparison preserves the feature and pricing review dated 12 October 2026. Vendor features, quotas and prices can change; use the linked vendor documentation for current terms. The comparison does not establish matched performance or production capacity.

MossCMS focuses on self-hosted headless publishing: visual schemas, predictable publication, workspace isolation, and a frontend-independent GraphQL API. The comparison below shows both what we offer and where competing projects offer more.

**Sanity's document quota remains a limit on paid Growth.** Drafts and release versions count as separate documents across datasets. At the document cap, new documents and drafts are blocked; ordinary per-request overage payments do not lift that cap. Growth needs the quota add-on, then Enterprise for a higher document allowance. See [Sanity's document-quota rules](https://www.sanity.io/docs/platform-management/plans-and-payments#document-quota).

For example, **10 billable Sanity Growth seats cost $150/month**; with the 50k-document quota add-on that becomes **$449/month**, before other usage costs. MossCMS adds no seat or total-entry license charge as content grows; infrastructure and maintenance still cost money, and comparable workload capacity has not been benchmarked.

Sanity also sets a useful feature benchmark: real-time editing, multiplayer presence, and visual editing are included in its [Studio offering](https://www.sanity.io/studio). MossCMS currently uses optimistic edit conflict detection and saved revision previews; it does not offer simultaneous collaborative editing or an in-place visual website editor.

### Current MossCMS limitations

- **Editorial features:** classic roles stay in place until an administrator turns on custom permissions. There is no real-time collaboration or general plugin marketplace. Rich text stays Markdown, with a visual editor for the supported subset and a lossless source mode. There is no visual site builder, and click-to-field mapping from the preview is not included. Content APIs use GraphQL; no REST content API is shipped.
- **Queries:** at most 100 entries per page, depth 12, 200 expanded selections, and 30,000 query characters. These are request limits, not caps on the total content stored. See [delivery API](../README.md#graphql-for-your-frontends) and [query limits](../api/app/query_limits.py).
- **Schemas and media:** 1–40 fields per object, at most five nesting levels, 1,000 items per list value, and 100,000 characters per text/rich-text value. Uploads default to 20 MiB per file. See [schema validation](../api/app/schema.py), [configuration](../api/app/config.py), and [image limits](images.md).
- **Operations:** SQLite is intended for one app instance; use PostgreSQL for multiple instances or heavy writes. Scheduling requires a running CMS. You operate backups, upgrades, monitoring, and recovery; this project offers no managed hosting or contractual uptime SLA. [Local 100k-entry benchmark and recovery results](benchmarks/RESULTS-2026-10-12.md) are available; larger cloud deployments and competitor performance comparisons remain unverified. See [production setup](../README.md#storage-and-production).
- **Example frontend:** the example website caps its bulk load at 2,000 entries. For larger collections, use the [typed streaming delivery client](delivery-client.md), which reads pages without a total-entry cap. Backend request bounds still apply.

**Where MossCMS stands out today**

- **Publication behavior is explicit.** Draft saves preserve live content and captured schedules. Failed schedules preserve the previous live snapshot and expose recovery actions. See the [publication contract](publication-contract.md).
- **Workspaces and delivery boundaries are built in.** Each workspace has its own schemas, content, and memberships. Expiring delivery tokens are scoped to content types; the delivery endpoint exposes only published content with private fields removed. See [teams](../README.md#admin-and-teams) and [delivery](../README.md#graphql-for-your-frontends).
- **The core ships together under MIT.** One application image serves the API and admin. Visual modeling, revisions, scheduling, localization, and local/S3 media are included without a paid feature tier. PostgreSQL is separate; SQLite is available for a single app instance. See [setup](../README.md#start) and [storage](../README.md#storage-and-production).

These are reasons to consider MossCMS; several competitors offer overlapping capabilities. The combination and its fit for your team matter more than a count of checkmarks.

### Competitive roadmap

The goal is to lead on editing quality, dependable team publishing, and predictable cost as content grows. Start by proving capacity and making adoption easy, then add the permissions and publishing controls teams need. Keep planned core features MIT licensed without per-seat or total-entry license charges; infrastructure still has costs.

Implementation has started; statuses below identify verified local slices and proposed work, without promising delivery dates. The [detailed competitive plan](planning/COMPETITIVE-ROADMAP-2026-10-12.md) defines scope, dependencies and acceptance gates; the [implementation record](planning/COMPETITIVE-IMPLEMENTATION-2026-10-12.md) links actual evidence and remaining work. Retain the existing review/integration process before shipping changes. P0 establishes trust, P1 improves adoption and publishing, and P2 expands validated workflows.
